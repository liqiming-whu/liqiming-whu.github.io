最近用 gpt-6-astra 整理文献报告、起草稿子，它查得细、写得全，挑不出什么事实错误。问题是读起来累：满篇"冻结基线""回归测试""验收矩阵"，每下一个结论，后面都要跟一串"不等于""不代表""不能据此推断"。我把稿子发给导师，他看了两段就问：这是 AI 写的吧？

网上早就有人拿这个开玩笑，还有人统计过，astra 文章里防御性表达能占到四分之一。与其每次手动改，不如写个 Skill 让模型自己改，这就是 [de-astra](https://github.com/liqiming-whu/agent-skills/tree/main/skills/de-astra)。

## Astra 腔长什么样

我归纳了三类毛病。

**一是软件工程黑话。** 它好像把做科研当成了上线一个服务：先冻结基线、搭测试夹具，再跑回归测试、做故障注入，最后过门禁、出验收矩阵，有问题就回滚。在生信分析里，这些事其实都有朴素的说法：

| Astra 的说法 | 正常的说法 |
|---|---|
| 冻结分析基线 | 固定输入数据和分析参数 |
| 执行回归测试 | 修改后重新运行分析，看结果是否一致 |
| 完成验收矩阵 | 逐项检查分析结果 |
| 故障注入 | 人为引入异常数据，看程序怎么处理 |
| 先灰度，再放量 | 先在部分样本上试，再推广到全部样本 |

**二是防御性表达太密。** 一句"下载量不等于独立用户数"已经够用，它还要接着写不代表活跃度、不能证明质量、不能据此推断满意度和安全性。真正重要的局限当然要写，这是科研的本分；但读者本来就不会误解的事，写五遍只会让人抓不住重点。

**三是硬译术语。** 它会把 track 译成"轨道"，把 call peak 译成"峰值调用"，reads 叫"读段"。同行看到这些词，得先在脑子里翻回英文才知道在说什么。

我自己的 [rp-xml-renderer](https://github.com/liqiming-whu/rp-xml-renderer) 的 README 也是 astra 帮忙写的，里面就有这么一句：

> 本地测试不等于实际手机视觉验收；宿主探针也不向真实模型发送消息。

意思其实很简单：本地测试只检查程序逻辑，界面效果还得在手机上看。

## de-astra 怎么改

Skill 只有一个 `SKILL.md`，没有脚本，规则大致是这几条：

- 工程黑话换成实验描述，但先判断这个词在本学科里有没有正规含义。统计里的"回归分析"、临床研究里的"基线特征"都是正经术语，原样保留。
- 每个结论先正面说清楚它说明了什么，局限合并成一句，放在该放的位置，论文里一般集中放进讨论部分。
- "不是 A，而是 B"只在读者真可能以为是 A 的时候才用，否则直接写 B。
- 同行习惯说英文的术语保留英文，比如 track、peak、reads、motif、spike-in、bigWig；软件名、命令和参数一个字都不动。测序、比对、可变剪接这些早已通行的中文词也不要反过来改成英文。

还有两条底线：**不增删任何事实、数据和结论**；如果删掉的某条局限可能影响结论，单独提醒我确认，由我决定要不要放回去。

改一段方法描述看看效果。原文：

> 利用 MACS2 对 ChIP-seq 读段执行峰值调用，并将所得峰值区域与输入对照的覆盖度信号一并加载至基因组轨道进行可视化审查。需要指出的是，峰值数量不等于真实结合位点数量，也不能直接代表结合强度。

改完：

> 用 MACS2 callpeak 对 ChIP-seq reads call peak，并将 peak 与 input 的 bigWig 信号一起载入基因组 track 查看。peak 数量只能粗略反映结合位点的多少。

## 安装和使用

Skill 放在 [agent-skills](https://github.com/liqiming-whu/agent-skills) 仓库里，MIT 许可证。把 `skills/de-astra` 整个目录复制到 Agent 的 skills 目录就能用，比如 Claude Code 是 `~/.claude/skills/`；在 claude.ai 上可以把这个目录打包成 zip，在设置里上传。

用的时候贴一段 astra 写的文字，说一句"去 astra 腔"。它会给出改写后的全文，再列几条主要改了什么。

## 另外两个去 AI 味的 Skill

给小说去 AI 味，我之前在 [my-operit-skills](https://github.com/liqiming-whu/my-operit-skills) 里写过两个 Skill，思路正好经历了一次转弯。

[rp-prose-polisher](https://github.com/liqiming-whu/my-operit-skills/tree/main/skills/rp-prose-polisher) 是早期的版本，走的是"量化达标"路线。它对正文做三段润色：内容自查、去 AI 味、去八股文。每段都配了 Python 脚本，检查比喻词密度、四字格连用、"一股……涌上心头"这类模板句、传球式对话。不达标就改，改完再测，最后出一份得分报告。改之前会自动备份原文件。

用了一阵发现，追分数会误伤好句子。有些"仿佛"用得恰到好处，有些重复是故意的，脚本分不出来，分数倒是上去了，读起来反而变平了。

于是有了 [chinese-prose-review](https://github.com/liqiming-whu/my-operit-skills/tree/main/skills/chinese-prose-review)。它保留了脚本定位问题、文件备份和修改后回验这些工程手段，但脚本只负责找出可疑位置，不打分，也不判通过或不通过，是不是真有问题由读稿的人判断。流程是先通读全文，挑出值得保留的句子，再去找毛病；只挑最影响阅读的几处说清楚原因；默认只审不改，得到授权才把修订另存为候选文件，原稿保持原样，并用哈希核对。

de-astra 也是同样的态度：规则是帮人看出问题的，最后看的还是读起来顺不顺。两者分工也很清楚，chinese-prose-review 管小说，de-astra 管论文、报告和技术文档。
